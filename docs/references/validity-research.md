# Technical validity and reference audit

Checked 21 November 2026. This note distinguishes historical evidence, current protocol requirements, and proposed experiments. It supports an educational simulation; it does not establish a vulnerability in a deployed Kerberos implementation.

## Assessment

A small INS project is academically viable as a controlled demonstration of replay protection in a Kerberos-inspired ticket system. The core can stand alone: measure identical authenticated requests with replay caching disabled and enabled, then examine clock-offset rejection separately. A synthetic service-password guessing experiment is a manageable extension. Present the contribution as a reproducible teaching implementation and measured comparison, without claiming a new authentication protocol, a new nonce defense, or an Active Directory benchmark. These are scope recommendations inferred from the sources below.

## What the historical critique actually supports

In the inspected Bellovin–Merritt text, “Replay Attacks” and “Secure Time Services” (printed pp. 4–5) address replays inside the timestamp window, then contemporary implementation problems with shared replay state. They explicitly discuss host-clock manipulation through unauthenticated time services and propose a session-key challenge/response alternative, acknowledging extra messages and retained challenge state. “Password-Guessing Attacks” (pp. 5–6) examines offline checking of password-derived ciphertext, principally login replies; it also notes tickets to password-keyed client services. This is historical motivation, not a claim that modern Kerberos replay caches can routinely be bypassed by ordinary skew. [Original author-hosted paper](https://www.cs.columbia.edu/~smb/papers/kerblimit.usenix.pdf).

## Current Kerberos requirements and simulation boundaries

Kerberos V5 application authentication uses a service ticket **plus an authenticator protected with its session key**. A stolen ticket alone is not the complete credential. Section 3.2.3 checks client identity, integrity, clock skew, and ticket validity. It requires a replay cache unless the application supplies suitable alternative replay protection; duplicate authenticators produce `KRB_AP_ERR_REPEAT`. Cache loss requires rejecting requests through the skew interval. Services sharing a principal must coordinate replay protection. [RFC 4120, §§3.2–3.2.3](https://www.rfc-editor.org/rfc/rfc4120#section-3.2.3).

Consequently, a ticket-only bearer mode is an intentionally weakened teaching baseline. A cleaner main experiment keeps ticket, authenticator, keys, clocks, request bytes, and validation fixed while toggling caching. Separately vary client/server offsets and report `SKEW`, expired, not-yet-valid, and duplicate outcomes distinctly. A fresh server challenge can protect the authentication exchange, but does not by itself remove clock-based ticket expiration. This experimental interpretation follows [RFC 4120](https://www.rfc-editor.org/rfc/rfc4120#section-3.2.3); do not label it a demonstrated attack on conforming Kerberos.

## Optional offline password-guessing extension

Real Kerberoasting obtains a service ticket encrypted under a service-account password-derived key, then guesses that password offline. Microsoft explicitly states that AES remains vulnerable with weak passwords and recommends stronger randomly generated service passwords or managed service accounts alongside AES. Thus “AES fixes Kerberoasting” is incorrect. [Microsoft’s Kerberoasting guidance, 11 October 2024](https://www.microsoft.com/en-us/security/blog/2024/10/11/microsofts-guidance-to-help-mitigate-kerberoasting/).

A synthetic encrypted service ticket with an integrity check can illustrate the same offline-verification principle. Label it **Kerberoasting-inspired**, unless implementing actual Kerberos ticket formats, string-to-key operations, and acquisition semantics. Hold the cipher and derivation parameters fixed when comparing weak and random passwords; report the exact candidate list, attempts, elapsed time, and stopping budget. “Not recovered within this budget” is supportable; “uncrackable” is not. If the chosen strong password is absent from a dictionary, that experiment establishes only absence from that tested dictionary.

AES is a cipher, while password guessing depends heavily on password entropy and key derivation. Kerberos AES in RFC 3962 uses salted PBKDF2 plus a Kerberos derivation step; an arbitrary AES-GCM/PBKDF2 demonstration is not a faithful implementation of those encryption types. [RFC 3962, §4](https://www.rfc-editor.org/rfc/rfc3962#section-4). Comparing algorithms is optional and requires documenting both derivations; avoid adding that scope to the minimum project.

## Detection claims and their limits

Windows Security Event **4769** records a TGS request on a domain controller, including ticket encryption type; it does not record the subsequent offline guesses. Microsoft documents schema changes beginning with January 2025 updates, so field availability is version dependent. [Microsoft event specification](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4769).

MITRE recommends investigating anomalous TGS volumes, unusual service-account targets, and RC4 requests. These are indicators requiring context; normal ticket issuance also creates events, and AES tickets remain guessable with weak passwords. An isolated simulation may produce analogous JSON logs, but must not claim they are actual Windows 4769 events or validated production detection. [MITRE ATT&CK T1558.003](https://attack.mitre.org/techniques/T1558/003/), [Microsoft guidance](https://www.microsoft.com/en-us/security/blog/2024/10/11/microsofts-guidance-to-help-mitigate-kerberoasting/).

## Minimum defensible deliverable

Recommended minimum: one isolated client, trusted ticket issuer, service, and replay driver; authenticated encrypted messages; an explicit timestamp window and ticket lifetime policy; replay cache on/off; deterministic clock-offset tests; and a compact result table. Add bounded synthetic offline guessing only after the replay study works. A challenge/response variant is an optional comparison of established approaches. Conclusions should describe the measured local model and its assumptions, with real Kerberos requirements cited separately.
