# Conference extension: replay-cache failure testing

Checked 21 November 2026. This is a bounded primary-source investigation following the existing proposal and validity audit. It used 15 focused search queries plus inspection of the strongest sources. It establishes substantial prior work; it does **not** establish an unoccupied literature gap, a deployed vulnerability, or likely acceptance at an unspecified conference. No implementation experiment was run for this note.

## Recommendation for the stated college context

The user reports a four-person team with approximately two active contributors, a small college conference, and an already-submitted topic whose changeability is uncertain. **Keep the topic and propose a manageable engineering/evaluation extension to the professors:** an atomic persistent cache for authenticated per-request replay identifiers, tested systematically across concurrency, expiry, clock offsets, and server restart. Present it as a reproducible student security experiment, with the implementation and measured behavior as its modest contribution. Do not promise a novel algorithm or acceptance. Whether this contribution meets the local conference's rules must be checked with the professors and actual call for papers.

The smallest useful extension has one service, two worker processes sharing one transactional persistent store, an injectable clock, a replay driver, and an operation counter. Compare no cache, volatile cache, and persistent atomic cache while holding authentication checks fixed. Measure accepted duplicates, rejected legitimate requests, restart behavior, and latency. Keep the synthetic password-guessing demonstration optional. No real MIT adapter, new cryptography, distributed cache, or learner study is required for this college project.

If the conference demands a substantive original research result, this implementation alone is insufficient evidence. A larger optional direction is a **stateful failure-injection and conformance benchmark** whose research unit is a sequence—authenticate, advance time, expire/reuse state, restart, change worker, replay—with minimized counterexamples. For a stronger systems/security paper, a pinned real MIT adapter and comparison against upstream tests would materially improve the evidence. Those are future-work options, not prerequisites for the stated college scope. These recommendations are inferences from the sources below, not validated novelty claims.

Possible working title: **Replay Protection Under Concurrency, Clock Skew, and Restart in a Kerberos-Style Simulator**. Retaining the current submitted title is also reasonable; describe these as refinements to its implementation and evaluation.

## What is already established

| Primary source inspected | Established result and consequence for this project |
| --- | --- |
| [RFC 4120 §3.2.3](https://www.rfc-editor.org/rfc/rfc4120.html#section-3.2.3) | Application authentication checks the authenticator and ticket, including skew. Replay caching is required unless suitable application protection replaces it. Duplicate authenticators produce `KRB_AP_ERR_REPEAT`. Lost replay history requires rejection until the skew interval passes. Servers sharing a service principal must share the replay cache or eliminate that dependency through their application protocols. These are existing requirements, not proposed defenses. |
| [MIT replay-cache improvement design](https://k5wiki.kerberos.org/wiki/Projects/Replay_cache_improvements) | This historical design already discusses process races, cache replacement, corruption, lost visibility across handles, reboot durability versus `fsync`, future timestamps, clock drift into the past, and performance/false-positive tradeoffs. It also reports a multiprocess benchmark and whole-file versus record-lock comparisons. Its description of a problematic “current implementation” belongs to the design's historical context; it must not be attributed to today's releases. |
| [MIT replay-cache documentation](https://github.com/krb5/krb5/blob/master/doc/basic/rcache_def.rst), [file2 format](https://web.mit.edu/KERBEROS/krb5-latest/doc/formats/rcache_file_format.html) | `file2`, introduced in 1.18, uses a hash-based file; `dfl` uses file2 with an effective-UID-based filename. The documented format uses exclusive file locking, fixed-size replay tags and timestamps, expanding hash tables, and reuse of expired slots. An ordinary persistent hash cache with locking would substantially repeat existing engineering. |
| [MIT `t_rcfile2.c`](https://github.com/krb5/krb5/blob/master/src/lib/krb5/rcache/t_rcfile2.c) | Existing tests already cover expiry/file growth, multiple processes inserting unique tags followed by replay checks, and a same-tag race in which exactly one process must succeed. Therefore “we test expiry and concurrent replay acceptance” is an especially weak novelty claim. |
| [MIT `replay.c`](https://github.com/krb5/krb5/blob/master/src/tests/replay.c), [runner](https://github.com/krb5/krb5/blob/master/src/tests/t_replay.py) | Upstream also constructs a real AP-REQ, accepts it, creates another server authentication context with the same replay cache, and checks duplicate rejection. It checks replay/reflection behavior for other Kerberos message types. A real-library replay test alone is also already present. |
| Davis, Geer and Ts'o, [*Kerberos With Clocks Adrift: History, Protocols, and Implementation*](https://www.usenix.org/legacy/publications/compsystems/1996/win_davis.pdf), 1996 | Clock synchronization limitations and a compatible challenge-response interpretation were studied and implemented in MIT Kerberos decades ago. “Remove clock dependence using a challenge” is not a safe novelty claim. |
| Butler et al., [*Formal Analysis of Kerberos 5*](https://www.cs.cmu.edu/~iliano/papers/tcs06.pdf), author-hosted 2006 preprint | Detailed symbolic analysis of a substantial portion of Kerberos 5 establishes authentication and confidentiality properties under a specified model. A small model cannot be presented as the first formal verification of Kerberos. |
| Sprenger and Basin, [*Refining security protocols*](https://people.inf.ethz.ch/basin/pubs/jsc2018.pdf) | The Isabelle/HOL development explicitly includes a Kerberos model with replay-cache entries, timestamps, expiry/purge, and injective agreement. Its clock advances through a tick event and its cache invariant retains entries while the corresponding timestamp is valid. This is a useful specification reference; it does not automatically prove an implementation correct under rollback, crashes, or deployment misconfiguration. |

The inspected sources leave a **candidate question**, not a verified gap: can a compact, reproducible sequence-based harness add useful coverage and actionable explanations beyond existing cache tests, particularly for interactions between expiry, rollback, restart, and worker configuration? The limited search did not identify a directly matching published differential/failure-injection suite. That negative search result is insufficient to claim that none exists. Before committing to a paper, inspect current MIT/Heimdal test trees, relevant issue histories, and forward/backward citations of the papers above.

## Optional stronger research contribution, if the pilot supports it

The intended artifact would be a scenario format, a state-machine oracle, controlled event scheduling, a real-implementation adapter, an educational reference implementation, and a reducer that removes events while preserving a failure. Its value would be experimentally demonstrated coverage and reproducibility, rather than a novel replay-cache algorithm.

Use a narrow initial scope: one machine, one service principal, two worker processes, one shared cache, injectable time, and process restart. Do not begin with distributed consensus, arbitrary network partitions, several cryptographic algorithms, or a new protocol. A single-host shared transactional store is a reasonable reference implementation choice, but is only an engineering choice.

The proposed benchmark should distinguish these properties:

1. **Authentication replay rejection:** after one successful acceptance, the same captured authenticator must not establish another accepted authentication while it remains otherwise valid, under the specified protection model.
2. **Legitimate-request availability:** fresh valid authenticators should be accepted outside declared recovery/quarantine periods. Record conservative rejection separately from replay acceptance.
3. **Application execution:** count committed protected operations separately from accepted authentications. Cache acceptance followed by a crash can lose an operation; an operation committed before an unrecorded response can produce ambiguous retries. Kerberos authentication replay protection is not an application-level exactly-once transaction guarantee. Do not assert one without a separate transactional design and proof/testing argument.

These are proposed operational definitions informed by the [RFC application-authentication requirements](https://www.rfc-editor.org/rfc/rfc4120.html#section-3.2.3). In the simulator, state the exact duplicate identity, timestamp bounds, ticket expiry/leeway, cache retention rule, and update order. In the MIT adapter, use real AP-REQ bytes and the library's validation path; a direct cache-store microbenchmark cannot establish end-to-end protocol conformance. Align assumptions before treating differing outcomes as bugs.

## Small experiment matrix

| Scenario family | Proposed sequence and observation |
| --- | --- |
| Race and visibility | Send one identical authenticated request to 2, 4, then 8 concurrent workers using a shared cache. Include split per-worker caches as an explicitly misconfigured control. Count acceptances and operation commits independently. |
| Expiry boundary | First use a valid request near each timestamp boundary; move time to just before, exactly at, and just after its last valid instant. Drive other traffic so expired storage slots really can be reused. Replay the original and compare with a fresh authenticator. |
| Time discontinuity | Combine forward advance, cache cleanup/reuse, then rollback into an old request's validity interval. Include a future-dated but initially acceptable authenticator. Specify the clock assumptions and whether rollback triggers rejection/quarantine. A monotonic timer alone does not repair every wall-clock ticket-lifetime decision. |
| Restart cutpoints | Terminate before replay-state insertion, after insertion, before operation commit, and after operation commit/before response. Test preserved replay state versus deliberate loss and documented recovery. Keep process crash and whole-machine/storage failure as separate fault models. |
| Topology/configuration | Restart one of two workers; vary shared versus isolated cache names/paths. Demonstrate configuration effects without calling deliberate principal/cache separation a library vulnerability. |

For every trial, retain the scenario seed, exact event order, logical and observed times, request identifier/hash, cache/worker configuration, acceptance reason, committed-operation count, and minimized counterexample. Report duplicate acceptance, legitimate rejection, recovery outage duration, p50/p95 latency, throughput, and storage use where meaningful. Repeat nondeterministic schedules and report denominators and run-to-run variability, not only successful screenshots.

Measure ordinary load separately from deterministic fault schedules. Record machine, OS/filesystem, dependency versions and exact upstream commit. Start with process kill/restart; it does **not** emulate power loss, lost device write caches, or a VM snapshot rollback. Do not label process-kill results “power-failure durability.” Testing those faults would require a separate storage/VM harness and declared persistence model.

MIT's [current file2 source](https://github.com/krb5/krb5/blob/master/src/lib/krb5/rcache/rc_file2.c) timestamps stored records using current time and serializes access with a file lock. That observation motivates careful clock/retention experiments; source inspection alone does not establish an exploitable flaw. Any apparent violation must survive full ticket/authenticator validation, the pinned version, correct configuration, and the stated attacker/environment assumptions.

## Stop/go checks before promising research novelty

Run a bounded pilot before expanding implementation:

1. Build a requirement-to-test table for the proposed families versus upstream `t_rcfile2.c`, `replay.c`, and other current tests/issues. If the proposed coverage is already present, change the question or stop the research claim.
2. Demonstrate the same scenario format and oracle against the simulator and one real MIT build. Prove the harness detects known injected errors and does not mark legitimate conservative rejection as a safety failure.
3. Produce at least one reproducible, minimized interaction result that teaches something beyond “turning off the cache permits replay.” A confirmed unreported implementation defect would be strong evidence, but is not required or promised. A useful alternative is a previously unmeasured, clearly explained safety/availability tradeoff with reusable artifacts and independent reproduction.
4. Ask a supervisor to assess whether the result differs materially from existing tests, design notes, and recent papers for the intended venue. If all results reproduce known behavior and offer no new coverage, methodology, or evaluated educational outcome, retain the good college project and drop the conference novelty claim.

For the small college venue, **go** with the modest simulator implementation/evaluation proposal if the professors confirm that kind of student contribution fits its rules. The four checks above apply before escalating to an original systems/security benchmark claim; they are not a demand to implement the larger agenda now. **No-go** for a new-protocol/new-cache-algorithm claim on the present evidence. ## Why a Kerberoasting detector is not the default extension

There is relevant prior work: Kotlaba, Buchovecká and Lórencz's [2021 paper](https://www.scitepress.org/PublishedPapers/2021/102028/102028.pdf) evaluates anomaly detection against traditional rules using real-organization AD events over six weeks. Aksüt's [2024 METU thesis](https://open.metu.edu.tr/handle/11511/112647) constructs a lab dataset and evaluates supervised methods; its linked [public repository](https://github.com/ysnakst/Dataset-for-Kerberoasting) contains `All4769Events.evtx` and analysis/evaluation code and explicitly identifies the logs as lab generated. Thus “first ML Kerberoasting detector” and “no public data exists” are unsupported claims. Repository availability does not itself establish a usable license, complete labels, or representative benign behavior; those need inspection before use.

Public real-world authentication data is not automatically suitable. The [LANL cyber1 release](https://csr.lanl.gov/data/cyber1/) provides de-identified authentication events and selected red-team events, but its documented authentication schema does not include full 4769 service-ticket encryption/SPN fields. It should not be advertised as a ready-made labeled Kerberoasting corpus without establishing that the required features and attack-specific labels exist.

The Australian government's [AD compromise guidance](https://www.cyber.gov.au/publication/detecting-and-mitigating-active-directory-compromises) explicitly explains that legitimate TGS use and Kerberoasting generate the same class of event; bursts and unusual service targets are indicators requiring context. A detector evaluates suspicious acquisition activity, not observation of subsequent offline password guesses.

Only choose this alternative after a data audit finds adequate labeled attack sessions, realistic benign activity and legal reuse terms. Compare simple encryption/volume/service-novelty rules before complex models; split by time and held-out sessions/users, prevent overlapping-window leakage, and report precision/recall and false alerts per user-day with low-volume and AES cases. A lab log can test functionality and controlled scenarios, but cannot establish enterprise effectiveness. This route changes the project into a telemetry/dataset study and is likely a larger scope jump than the replay benchmark.
